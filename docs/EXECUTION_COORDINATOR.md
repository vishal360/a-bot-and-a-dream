# Stage 4: isolated durable execution coordinator

`src/execution-coordinator.ts` is a deliberately narrow, standalone SQLite fixture/testnet OMS kernel. It does **not** import Paper, connect server routes, contain an HTTP client, supply a signer, or provide production trading. MAINNET is unconditionally refused, irrespective of flags. Supported environments are exactly `fixture` and `testnet`; testnet requires chain ID `300`. Fixture bindings are synthetic and must never be wired to a real venue.

## Trust boundary and units

The caller injects `VenueSigningAdapter` and verified account/evidence objects. `verified: true` is an explicit **trusted caller attestation**, not signature verification implemented here. Never construct these objects from untrusted HTTP payloads. A future read adapter must independently verify venue/account/chain/generation, authenticated provenance, chronology, and completeness before crossing this boundary. A snapshot paired with terminal evidence must include that event's resulting position, available balance and gross exposure; advancing a sequence number alone does not establish this fact.

Quantities, price bounds, notional, margin, equity, balances, timestamps and nonces use safe integers. `quantity * worstPrice` is a conservative risk-unit notional. These are **abstract consistent fixture units, not USDC**, and no decimal-scale conversion to a venue's size/price decimals is included. The optional testnet bridge provides exact base/price atom conversion and refuses heterogeneous product scales, but does not supply an audited USD/USDC normalization layer. Do not enable real execution without that reviewed layer and trusted snapshot collectors. All configured caps are required and positive. Account snapshot availability must not exceed equity. Worst price must be enforced as an actual adapter limit; unbounded market execution cannot satisfy this contract.

Binding contains environment, account ID, API key ID, chain ID, generation. Authorization and fresh verified reconciliation are process-local and reset at construction. Snapshot sequence/time high-water is durable **per account across API keys and connection generations**, and rollback/conflicting sequence economics are rejected. Account economics at an identical sequence must match; key-specific nextNonce is deliberately excluded from this shared economics fingerprint. New evidence invalidates every other session's older account baseline before it can open. Generation identity is still exact on each injected session/evidence; permanent retirement of old generations is the trusted connection manager's responsibility, not an automatic policy inferred from opaque generation names. Account reservations aggregate across keys, independently of Paper and of any account risk implementation. They add full pending worst-case notional to the verified account gross baseline and full pending margin to available/equity checks. This can double-count existing fills or reducing orders deliberately; conservative false blocks are preferable to understated risk. No leverage assumptions relax these caps.

## Submission protocol

1. `reconcileAccount(snapshot)` accepts fresh, verified, matching account evidence.
2. `authorizeSession(binding)` authorizes only this process session. `revokeSession()` closes it again.
3. `prepare(intent)` atomically checks caps, pending order count and pending reductions, then persists an immutable exact canonical fingerprint and full reservation. Identical client ID retries return the existing order; any immutable field change is rejected forever, including terminal IDs.
4. `submit(clientId)` atomically acquires the API key's durable owner/fence/TTL lease, persists a unique `(key, nonce)` ownership record, advances a durable nonce high-water from the verified snapshot, and stores `submitting` **before** invoking the adapter.
5. The injected adapter must check `assertCurrentLease()` immediately before actual signing/dispatch and must not retry internally. It receives explicit nonce and fencing token. Accepted responses containing `transactionId` move only to `acknowledged`, never `filled`. The transaction reference is stored separately; it is **not** a venue order ID. Verified reconciliation must subsequently establish the genuine order ID and match the accepted transaction reference.
6. An exception, timeout, malformed response or expired lease yields `unknown`. Unknown holds full reservation, blocks new opens, and is **never resent automatically**, even if the remote acceptance may have succeeded. Calling submit again is a read-only status operation for any non-prepared order.

One active lease serializes sends per API key across SQLite connections. TTL expiration converts abandoned submitting work to unknown; old fence/owner callbacks cannot acknowledge it or clear a newer lease. The lease is intentionally not renewed during arbitrarily long requests: expiry sacrifices availability for safety. This is cooperative fencing: an untrusted adapter can ignore its callback, and a local fence cannot physically undo already dispatched network bytes. Hence uncertain requests always remain unknown and no exactly-once remote-delivery claim is made.

On construction all surviving `submitting` orders become `unknown`, affected leases are fenced, and all surviving `prepared` orders become **local-cancel-only**. Thus a crash anywhere around dispatch cannot result in a blind replay. `cancelPrepared` releases only when state is still prepared, nonce is null and no nonce ownership exists, proving this coordinator never dispatched. This conservative startup also interrupts another active coordinator if both construct against a shared database: do not treat construction as a harmless read-only observer.

## Reconciliation and lifecycle

Lifecycle: `prepared -> submitting -> acknowledged | unknown`, followed by explicit verified `acknowledged`, `partial`, `filled`, `canceled`, or `rejected` evidence. `partial` retains the **entire** worst-case reservation. `unknown` may resolve only through evidence; never infer rejection from elapsed time or a missing lookup result.

`reconcileOrder(evidence, snapshot)` requires matching account binding, durable nonce, genuine venue order ID, explicit venue transaction or order proof reference, fresh evidence, and a fresh matching account snapshot whose sequence and observation time advance beyond the order's prior accounted evidence. That snapshot must reflect the event before terminal reservation release. The cumulative fill set must contain every prior fill, have unique venue fill IDs and never exceed requested quantity. Filled requires exactly requested quantity. Partial requires positive quantity below requested. Acknowledged/rejected require zero fills. Cancellation may include partial fills. Exact duplicate evidence is idempotent; global per-key fill IDs cannot be reused with different ownership or quantity.

Conflicting terminal states, regressing fills, reused fill identities, contradictory evidence IDs or quantities latch a persistent conflict and clear session authorization. Existing holds are not released on invalid evidence. A terminal order already released on previously trusted evidence cannot be unfilled by contradictory evidence; its conflict still blocks all further submissions and new reservations for the account pending external operator investigation. No automatic conflict-clear API exists. Re-authorizing a session cannot bypass that durable latch.

Reduce-only orders require the correct side of a verified signed position. Requested quantity plus full pending reductions may not exceed the position. Oversized requests are **rejected**, not silently resized; there is no flip path. Proven reduce-only requests are exempt from the aggregate gross-notional cap to permit exits when the account already exceeds it, but remain subject to per-order quantity/notional, order-count and available-margin guards. A zero-additional-margin reducing adapter should supply `margin: 0`. Venue adapter must also enforce native reduce-only to protect against position movement outside this coordinator. Different snapshot sequences invalidate precomputed prepared decisions instead of quietly reusing stale risk.

## Explicit gaps / not production readiness

`status()` always reports `NATIVE_PROTECTION_GAP`. There is no verified native stop placement, bracket/stop pairing, replacement, trigger monitoring or protection recovery; no claim of protected positions is made. Other missing production components include authenticated evidence collectors, automatic transaction/order lookup, decimal normalization, key custody, external order detection, leverage/margin models, fees/funding/liquidation/slippage model, operator conflict resolution, schema migration tooling, and operational recovery orchestration. The kernel assumes trusted local SQLite storage; validation detects malformed rows and broken invariants but is not tamper authentication. Database errors and corruption fail closed rather than reconstructing state from guesses.

Tests use **only an injected fake adapter**, never HTTP or live credentials. Run with Bun explicitly on PATH (Windows PowerShell):

```powershell
$env:PATH = "$env:USERPROFILE\.bun\bin;$env:PATH"
& "$env:USERPROFILE\.bun\bin\bun.exe" test ./tests/execution-coordinator.test.ts
& "$env:USERPROFILE\.bun\bin\bun.exe" node_modules/typescript/bin/tsc --noEmit
```
